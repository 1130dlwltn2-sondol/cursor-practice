# Part 5. Rules와 팀

## 52. 팀 도입과 운영

Cursor를 팀 단위로 도입하면 개인 생산성 도구에서 팀 워크플로로 성격이 바뀐다. 각자 다른 프롬프트를 쓰고, 각자 다른 규칙을 쓰고, 각자 다른 도구를 쓴다면 코드 리뷰에서 충돌이 늘어난다. 팀 도입의 핵심은 컨텍스트를 공유하는 것이다.

Teams 플랜에서 제공하는 팀 기능은 크게 세 가지다. 첫째, 공유 컨텍스트다. 팀 규칙과 MCP 설정을 저장소에 넣어 전원이 같은 기준으로 에이전트를 쓰게 한다. 둘째, 팀 규칙의 중앙 관리다. 코딩 스타일, 네이밍, 금지 패턴 같은 기준을 한 곳에서 정하고 배포한다. 셋째, 사용량 분석이다. 팀원별 AI 사용량을 확인해 비용을 관리하고, 병목이 생기는 구간을 파악한다.

팀 도입의 단계별 순서는 다음과 같다.

1. 파일럿 그룹을 정한다. 2~3명 정도의 소규모로 시작해 실제 업무에 적용해 본다.
2. 프로젝트 규칙(.cursor/rules)을 만든다. 파일럿 기간에 반복해서 말하게 되는 지시들을 규칙으로 옮긴다.
3. MCP 서버 설정을 저장소에 공유한다. 문서 검색, 이슈 트래커 같은 공통 도구를 전원이 같은 방식으로 쓰게 한다.
4. 터미널 승인 정책을 정한다. 자동 실행 허용 범위와 매번 확인이 필요한 명령을 문서화한다.
5. 사용량을 한 달 정도 보고 요금제를 조정한다. 실제 사용 패턴을 본 뒤 플랜을 결정하는 것이 합리적이다.

규칙과 설정을 저장소에 넣는 것은 팀 도입에서 가장 효과가 큰 한 걸음이다. 새 팀원이 합류하면 프로젝트를 클론하는 것만으로 같은 규칙, 같은 MCP, 같은 승인 정책을 갖게 된다. "우리 팀은 이렇게 써"라는 설명이 파일 몇 개로 대체된다.

운영하면서 생기는 전형적인 문제도 있다. 첫째, 규칙이 쌓이면서 서로 모순되는 경우다. 분기마다 규칙 파일을 리뷰하고, 쓰지 않는 규칙은 과감히 지운다. 둘째, 에이전트 결과물의 품질 편차다. 시니어는 에이전트를 조율하는 데 익숙하지만, 주니어는 결과물을 그대로 믿는 경우가 있다. 코드 리뷰 기준을 "AI가 만들었든 사람이 만들었든 같은 기준"으로 명확히 해 두자. 셋째, 민감 정보 유출이다. 에이전트 입력에 비밀 키나 고객 데이터를 붙여넣지 않는 규칙을 팀 차원에서 정하고, MCP 권한도 읽기 전용부터 시작한다.

팀 도입 성공의 지표는 거창하지 않다. 에이전트에게 맡기는 작업의 비율이 늘고, 코드 리뷰에서 스타일 지적이 줄고, 온보딩 기간이 짧아지면 제대로 굴러가고 있는 것이다.

핵심 정리
- 팀 도입의 핵심은 규칙과 MCP 설정을 저장소에 넣어 컨텍스트를 공유하는 것이다.
- 소규모 파일럿으로 시작해 규칙, 도구, 승인 정책을 순서대로 정착시킨다.
- 규칙 충돌 정리, AI 결과물 리뷰 기준, 민감 정보 보호를 운영 과제로 관리한다.
