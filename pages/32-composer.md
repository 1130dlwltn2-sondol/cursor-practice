# Part 3. Chat과 코드베이스 이해

## 32. Composer

Composer는 여러 파일을 한 번에 편집하는 모드다. Chat이 "말로 설명하는" 데서 그친다면, Composer는 "직접 고치는" 쪽에 가깝다. 하나의 지시로 여러 파일에 걸친 변경을 수행한다. Cursor 3.0에서는 Agents Window가 이 역할을 계승해서, 여러 에이전트를 병렬로 돌리며 각자 파일을 맡기는 방식도 가능해졌다.

사용법은 Chat과 비슷하게 시작한다. Composer를 열고(단축키는 설정에서 확인), 하고 싶은 변경을 문장으로 적는다. 예를 들어 "로그인 API의 응답 형식을 바꾸고, 그걸 쓰는 프론트 코드도 함께 고쳐 줘" 같은 지시다. AI가 변경할 파일 목록을 보여 주고, 확인을 받으면 실제로 편집한다.

실습 예제를 해보자. 간단한 프로젝트에서 함수명을 바꾸는 작업을 Composer에게 맡긴다.

```
calculate_total이라는 함수명을 calc_order_total로 바꾸고,
이 함수를 호출하는 모든 곳도 함께 수정해 줘
```

Composer는 해당 함수가 정의된 파일과 호출하는 파일들을 찾아서 일괄 수정한다. 사람이 직접 하면 놓치기 쉬운 호출처까지 찾아주니, 이런 기계적인 변경에 특히 잘 맞는다.

Composer가 작업을 마치면 변경 내용을 하나씩 확인해야 한다. diff 보기로 어떤 파일의 어떤 줄이 바뀌었는지 살펴보고, 이상이 없으면 수락한다. 전수 확인이 원칙이다. AI가 "다 고쳤다"고 해도 눈으로 보지 않고 넘어가면 나중에 찾기 어려운 버그가 된다.

Composer와 에이전트 모드의 차이도 짚어 두자. Composer는 지시받은 편집을 수행하는 데 초점이 있고, 에이전트 모드는 터미널 실행과 디버깅까지 포함한 더 넓은 작업을 맡는다. 간단한 다중 파일 편집은 Composer로, 테스트 실행과 수정이 얽힌 작업은 에이전트 모드로 나누는 것이 실무에서는 편하다. 자세한 에이전트 모드는 4부에서 다룬다.

주의점이 있다. Composer에게 너무 큰 변경을 한 번에 맡기지 말자. "전체 구조를 바꿔 줘" 같은 지시는 결과물의 일관성이 떨어진다. 파일 몇 개 단위로 쪼개서 순차적으로 지시하는 것이 안전하다. 각 단계마다 diff를 확인하고 넘어가면, 문제가 생겼을 때 어디서 틀어졌는지 바로 알 수 있다.

또 하나, Composer가 파일을 새로 만들 때는 위치를 지정해 주는 것이 좋다. "src/utils/ 아래에"처럼 경로를 명시하면 엉뚱한 곳에 파일이 생기는 일을 막을 수 있다.

핵심 정리
- Composer는 하나의 지시로 여러 파일을 한 번에 편집한다. Cursor 3.0부터는 Agents Window가 이 역할을 계승했다.
- 작업이 끝나면 diff를 전수 확인하고 수락한다.
- 큰 변경은 파일 몇 개 단위로 쪼개서 순차적으로 지시한다.
