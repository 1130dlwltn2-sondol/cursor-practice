# Part 4. 에이전트 모드로 통째로 만들기

## 42. 디버깅 자동화

디버깅은 전통적으로 개발자가 가장 많은 시간을 쓰는 작업이다. 에러 메시지를 읽고, 스택 트레이스를 따라가고, 재현 조건을 좁히고, 원인을 추측하고, 고치고, 다시 돌려보는 사이클이 반복된다. Cursor의 에이전트는 이 사이클을 자동화하는 데 쓸 수 있다. 에러 메시지와 관련 파일을 함께 주면 원인을 찾고 수정안을 제안하고 실행까지 이어간다.

에이전트에게 디버깅을 맡길 때 효과적인 흐름은 다음과 같다.

1. 에러가 난 상황을 그대로 전달한다. 에러 메시지 전문을 복사해서 붙여넣는 것이 좋다.
2. 재현 방법을 함께 적는다. "버튼을 두 번 누르면 이렇게 된다" 같은 설명이다.
3. 의심 가는 범위를 한정해 준다. 관련 파일은 @ 멘션으로 지정한다.
4. 에이전트가 원인 후보를 제시하면, 수정 전에 먼저 원인 분석을 읽어본다.
5. 수정안을 diff로 확인하고 승인한 뒤, 에이전트에게 재실행으로 검증하게 한다.

실습: 일부러 만든 버그를 잡아보자

아래 코드를 프로젝트에 붙여넣고, 에이전트에게 디버깅을 맡기는 연습을 해보자.

```javascript
// src/utils/cart.js
function calcTotal(items) {
  let total = 0;
  for (let i = 0; i <= items.length; i++) {
    total += items[i].price;
  }
  return total;
}
```

1. 위 함수를 호출하는 코드를 작성하고 실행해 TypeError가 나는 것을 확인한다.
2. 에이전트 입력창에 다음처럼 적는다.

```text
@src/utils/cart.js 에서 calcTotal을 호출하면
TypeError: Cannot read properties of undefined 오류가 난다.
원인을 찾아서 고쳐줘. 고친 뒤에는 간단한 테스트로 동작을 확인해줘.
```

3. 에이전트가 반복 조건 i <= items.length를 지적하고 i < items.length로 고치는 과정을 diff로 확인한다.
4. 에이전트가 제안한 테스트(빈 배열, 정상 배열 케이스)를 승인하고 결과를 확인한다.

이 실습에서 눈여겨볼 점은 원인 분석과 수정을 분리해서 확인하는 것이다. 에이전트가 바로 코드를 고치려고 하면 "수정하기 전에 원인만 먼저 설명해줘"라고 요청할 수 있다. 분석이 맞는지 판단하는 습관이 쌓이면 에이전트의 디버깅 제안을 빠르게 걸러낼 수 있다.

에이전트 디버깅이 잘 통하는 경우와 그렇지 않은 경우도 있다. 에러 메시지가 명확하고 재현이 쉬운 경우는 성공률이 높다. 반대로, 여러 시스템이 얽힌 타이밍 버그나 환경 의존적인 문제는 에이전트가 한 번에 잡기 어렵다. 이럴 때는 범위를 좁혀서 "이 파일의 이 함수만 봐줘"처럼 단계를 나누는 것이 좋다.

디버깅 시 주의점도 정리해 두자. 첫째, 에러 메시지에 개인정보나 비밀 키가 포함되어 있지 않은지 확인하고 전달한다. 둘째, 에이전트가 고친 코드가 증상을 가리는 식(에러를 try-catch로 덮는 식)인지, 근본 원인을 고치는 것인지 구분하자. 셋째, 한 번의 지시로 너무 많은 수정을 허용하지 말고, 원인 하나씩 확인하는 리듬을 유지한다.

핵심 정리
- 에러 메시지 전문과 재현 방법, 관련 파일을 함께 주면 에이전트 디버깅의 성공률이 올라간다.
- 원인 분석을 먼저 확인하고 수정을 승인하는 순서를 지키면 잘못된 수정을 막을 수 있다.
- 복잡한 문제는 범위를 좁혀 단계별로 맡기고, 증상 가리기와 근본 원인 수정을 구분한다.
