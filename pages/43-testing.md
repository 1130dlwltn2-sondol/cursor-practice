# Part 4. 에이전트 모드로 통째로 만들기

## 43. 테스트 자동화

코드를 고치는 속도가 빨라지면 테스트가 병목이 된다. 수정할 때마다 손으로 테스트를 짜고 돌리는 일은 번거롭고, 생략하면 회귀 버그가 숨어든다. 에이전트는 테스트 작성과 실행도 맡을 수 있다. 기존 코드를 읽고 테스트 케이스를 만들고, 돌려보고, 실패한 부분을 다시 고치는 흐름이 한 세션 안에서 돌아간다.

에이전트에게 테스트를 맡기는 일반적인 순서는 이렇다.

1. 테스트 대상 코드와 기존 테스트(있다면)를 @ 멘션으로 지정한다.
2. "이 함수의 테스트를 만들어줘. 정상 케이스, 경계 케이스, 실패 케이스를 포함해줘"처럼 범위를 정해준다.
3. 테스트 프레임워크와 네이밍 규칙을 지정한다. Rules로 고정해 두면 매번 말할 필요가 없다.
4. 에이전트가 테스트를 만들고 실행한 뒤 결과를 보여준다.
5. 실패한 테스트가 있으면 원인 분석을 요청하고, 코드와 테스트 중 어느 쪽이 틀렸는지 판단한다.

실습: 유틸 함수 테스트를 통째로 맡기기

src/utils/slug.js에 다음 함수가 있다고 가정하자.

```javascript
export function slugify(title) {
  return title
    .toLowerCase()
    .replace(/[^a-z0-9가-힣\s-]/g, "")
    .trim()
    .replace(/\s+/g, "-");
}
```

1. 에이전트에게 다음 지시를 준다.

```text
@src/utils/slug.js 의 slugify 함수에 대한 테스트를 만들어줘.
jest를 쓰고, 테스트 파일은 src/utils/slug.test.js로 해줘.
정상 입력, 한글 입력, 특수문자 입력, 빈 문자열 같은 케이스를 포함해줘.
```

2. 에이전트가 테스트 파일을 만들고 npm test를 돌린 뒤 결과를 보여준다.
3. 실패한 케이스가 있으면 에이전트에게 "실패 원인을 먼저 설명해줘"라고 요청한다.
4. 정규식이 한글을 허용하는지, 빈 문자열이 "-"로 바뀌는지 같은 경계 동작을 확인하고 필요하면 케이스를 추가해 달라고 한다.

이 실습의 포인트는 테스트 케이스 선택의 주도권을 쥐는 것이다. 에이전트는 무난한 케이스를 잘 만든다. 하지만 도메인 특유의 경계(예: slug가 URL에 들어갈 때 허용되는 문자)는 사람이 알려줘야 한다. 첫 테스트는 에이전트에게 맡기고, 빠진 케이스는 사람이 덧붙이는 분업이 현실적이다.

테스트 자동화에서 주의할 점도 있다. 첫째, 테스트를 에이전트가 만드는 만큼, 테스트 자체의 품질도 검토 대상이다. 어설픈 assertion(항상 통과하는 테스트)이 끼어들 수 있다. 둘째, 기존 테스트를 함부로 고치지 말라는 규칙을 Rules에 넣어두자. 테스트가 실패했을 때 코드를 고쳐야 할지 테스트를 고쳐야 할지는 사람이 판단해야 한다. 셋째, 느린 통합 테스트나 외부 의존성이 있는 테스트는 자동 실행 목록에서 빼고 수동으로 돌리는 편이 안정적이다.

핵심 정리
- 에이전트는 테스트 작성부터 실행, 실패 분석까지 한 흐름으로 처리할 수 있다.
- 경계 케이스 선택은 도메인 지식이 필요한 영역이므로 사람이 보완하는 분업을 권장한다.
- 테스트 품질도 검토 대상이며, 기존 테스트 수정에 대한 규칙을 미리 정해두자.
